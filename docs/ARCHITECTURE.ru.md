# Архитектура Random Client

> **Языковая политика:** английская версия документа является нормативной.
> Этот файл — синхронизированный перевод и не добавляет самостоятельных
> требований.

## Назначение и статус документа

Документ определяет обязанности компонентов RandomClient, runtime-потоки,
переходы состояний, протокольные допущения и инварианты безопасности.
`docs/Random.h` определяет интерфейс и поведение смарт-контракта Random. Rust-код
реализует оба документа. README является основным пользовательским руководством.

Любое известное противоречие между этими источниками устраняется в том же
изменении.

## Системный контекст

RandomClient — долгоживущий provider-бот. Один процесс управляет одной Qubic
identity и поддерживает по одной provider-цепочке выбранного уровня залога в
каждом из трёх стримов Random.

Свежая цепочка начинается с `zero reveal + non-zero commit`. Каждый обычный
вызов раскрывает предыдущее 4096-битное прообразное значение и фиксирует новое.
Упреждающий terminal-вызов передаёт известный outstanding preimage с нулевым
commit; контракт учитывает reveal и удаляет provider в конце тика.

Внешние границы — Qubic HTTP RPC, Bob JSON-RPC или QubicLightNode gRPC; контракт
Random с индексом `3`; операционная система для безопасной случайности,
защищённой памяти seed, времени, stdin и сигналов завершения.

## Карта компонентов

| Компонент | Ответственность |
| --- | --- |
| `src/main.rs` | Запустить Tokio, разобрать конфигурацию и вернуть результат процесса. |
| `src/app.rs` | Создать wallet, backend и engine; преобразовать сигналы ОС в корректное завершение. |
| `src/config.rs` | Разобрать CLI, нормализовать endpoints, проверить залог и интервалы мониторинга и хранить seed в заблокированной и обнуляемой памяти. |
| `src/backend.rs` | Определить транспортно-независимый порт и адаптировать RPC, Bob и gRPC, включая отложенные проверки данных тика. |
| `src/bob.rs` | Декодировать различные JSON-формы ответов Bob. |
| `src/http.rs` | Ограничивать тела HTTP-ответов и сохранять необходимые форматы запросов RPC/Bob из SCAPI. |
| `src/contract.rs` | Хранить константы Random и строгие wire-кодеки. |
| `src/entropy.rs` | Генерировать 4096-битные preimages и KangarooTwelve commitments. |
| `src/engine.rs` | Владеть состояниями трёх стримов, планированием тиков, restart по статусу, retry, счётчиками доставки, проверкой данных тика, жизненным циклом эпохи и drain. |
| `src/console.rs` | Форматировать небольшие runtime-логи без секретных данных и текущий snapshot счётчиков доставки. |
| `proto/lightnode.proto` / `build.rs` | Определить и сгенерировать минимальный клиент QubicLightNode. |

Проект остаётся плоским и небольшим. `NetworkBackend` — единственный выбираемый
через CLI транспортный порт; engine не содержит специфичных для backend ветвей.
SCAPI отвечает за wallet/identity, построение и подпись транзакций, а также за
wire-модели RPC. Необходимые HTTP-вызовы используют небольшой транспорт с
ограничением размера ответа, поскольку клиенты закреплённой версии SCAPI не
предоставляют такого лимита. Пути RPC, payload и JSON-RPC-конверты Bob сверяются
с этой реализацией тестами совместимости на локальном сервере.

SCAPI закреплён на неизменяемой ревизии с отключёнными default features.
Клиент использует его Qubic API без опционального native-модуля WalletConnect,
CLI и графа зависимостей WalletConnect/Ethereum. Это исключает неиспользуемые
HTTP-стеки из клиента, сохраняя поведение подписания и протокола SCAPI.

## Поток запуска

1. Конфигурация принимает 55-символьный lowercase seed, backend, endpoint,
   уровень залога, две настройки мониторинга и две настройки окон эпохи.
2. Seed без CLI-аргумента читается без echo или из перенаправленного stdin. Его
   байты блокируются, скрываются из `Debug` и обнуляются; ошибка блокировки
   памяти прерывает запуск. Временные буферы stdin, которыми владеет клиент,
   обнуляются и при ошибках, включая частичный ввод после неудачного чтения.
   Локальная копия `rtoolbox` с исправлением, используемая `rpassword`, при
   уничтожении строки очищает всю её текущую область памяти, включая символы,
   удалённые при редактировании в терминале. Это не охватывает предыдущие
   области памяти, освобождённые при увеличении строки.
3. App получает `QubicWallet`, создаёт выбранный backend и engine, затем удаляет
   wrapper seed.
4. Engine создаёт ровно три слота для стримов `0`, `1`, `2` на уровне
   `log10(collateral)`.
5. Стрим не запускается, пока успешно декодированный provider-status ответ,
   запрошенный на допустимом тике, не сообщит отсутствие точной пары
   `(stream, tier)` и не закончится warmup эпохи.

Занятый при запуске слот не перезаписывается. Процесс не сохраняет preimages и
ждёт исчезновения точного слота.

## Основной цикл

Приложение выбирает интервал опроса 20 мс для локального кеша тиков gRPC
и 100 мс для RPC и Bob. Оно передаёт интервал независимому от транспорта
engine, который пропускает упущенные пробуждения вместо накопления догоняющих циклов:

1. Получает свежие метаданные тика с таймаутом две секунды. Ошибка прерывает
   только текущий цикл и повторяется; старый тик не подставляется для
   планирования отправки.
2. Обновляет фазу epoch/warmup/drain по номеру эпохи, initial tick и UTC.
3. Забирает предыдущий provider-status запрос и независимые broadcast-задачи.
4. Применяет свежее наблюдение статуса к точному состоянию `(stream, tier)`.
5. В активной фазе запускает допустимые отсутствующие слоты и продолжает
   известные цепочки.
6. При pre-epoch drain или shutdown замораживает обычное планирование и создаёт
   безопасные terminal reveals.
7. Помечает пропущенные вызовы, отправляет допустимые вызовы, завершает drain и
   удаляет старые принятые вызовы.
8. Запускает не более одного provider-status запроса с интервалом между
   запусками не менее 500 мс.
9. Удаляет просроченные проверки мониторинга, забирает завершённую проверку и
   запускает не более одной допустимой проверки, если нет drain или shutdown.

Статус, broadcasts и одна отложенная проверка данных тика выполняются
отдельными ограниченными Tokio-задачами. Медленный запрос не сериализует
остальные стримы. Engine отменяет status-, broadcast- и tick-data-задачи при
reset и все свои задачи при drop. Cancellation-safe
наблюдатель shutdown остаётся активен во время ожидания tick-вызовов и отменяется
при уничтожении future метода run, в том числе при внешней отмене.
Отправка транзакций предшествует новым запросам статуса и мониторинга;
ускоренный опрос тика не повышает лимит provider-status запросов.

## Инварианты контракта и планирования

- Есть ровно три независимых стрима.
- Стрим `s` использует только тики `tick % 3 == s`.
- Последовательные вызовы непрерывной цепочки разделены ровно тремя тиками.
- Первый target — первый тик нужного стрима не раньше `current_tick + 6`, а
  после restart — не менее чем через три тика после старого подписанного
  хвоста. Его broadcast может идти одновременно с доставкой старого хвоста.
- Планирование остаётся на шесть тиков вперёд. First commit (нулевой reveal)
  становится доступным для broadcast за шесть тиков до неизменного target.
  Обычные и terminal reveals доступны только за четыре тика до target, включая
  retries и сохранённые старые хвосты. Общий диспетчер проверяет это до передачи
  подписанных байтов любому backend. Если polling пропустил границу, вызов
  отправляется, пока target остаётся в будущем.
- Одного успешного принятия backend достаточно. Ошибка обычной или pre-epoch
  drain отправки повторяется неизменными подписанными байтами до target. Reveal,
  commitment, tick, signature и transaction ID не пересоздаются и не
  перенацеливаются. На target или позже отправки нет.
- В `Starting` и `Active` принятый first commit или обычный вызов получает
  одну дополнительную отправку тех же подписанных байтов: first commit за
  четыре тика до target (или за три, если polling пропустил границу), обычный
  reveal за три тика до target. Core формирует набор
  транзакций target `T` на `T - 2`; на этой границе публикации или позже новая
  дополнительная попытка не начинается. Эта попытка распространения
  не меняет принятие, счётчики доставки и дедупликацию мониторинга; ошибка
  логируется без следующего повтора. Для старого замороженного хвоста и во
  время drain новые дополнительные попытки не начинаются; terminal reveals
  исключены. Подготовленная replacement-цепочка следует обычной политике
  дополнительной отправки. Незавершённая попытка
  отменяется на target, при удалении цепочки, сбросе эпохи или drop процесса.
  Обычный reveal, впервые принятый на `T - 4`, ждёт `T - 3` для дополнительной
  попытки. При позднем первом принятии на `T - 3` одна дополнительная попытка
  ещё возможна на том же тике; на `T - 2` она уже не начинается.
- Для принятия RPC нужны одновременно непустой идентификатор транзакции и
  положительное значение `peersBroadcasted`. Нулевое или недопустимое число
  peers считается временной ошибкой доставки и сохраняет retry неизменных байтов.
- Планирование продолжается без ожидания подтверждения каждого target.
  Отсутствие, foreign target или старый локальный `lastUpdateTick` создаёт
  подозрение, но в течение первых двух подтверждений планирование продолжается.
  Цепочка замораживается только после третьего согласованного успешно
  декодированного наблюдения, запрошенного на более позднем тике. Продвижение
  статуса снимает подозрение; повторный или регрессирующий тик запроса не
  увеличивает его, а регресс локального тика считается stale.
- В состояниях `Starting` и `Active`, если обязательный target текущей цепочки
  наступил без принятия backend, локальная цепочка останавливается и ждёт
  status-запроса, начатого после разрыва. Истечение сохранённого старого вызова
  не может остановить replacement. `Restarting` следует описанному ниже
  правилу замороженного хвоста.
- Принятие backend подтверждает только submission, а не исполнение контрактом.
- Preimages используют случайность ОС, commitments — KangarooTwelve; секреты
  остаются только в памяти процесса.

Вход процедуры всегда имеет 544 байта: 512 байт reveal и 32 байта commitment.
Вход `GetProviderStatus` — raw 32-byte public key, выход — строгая выровненная
структура на 680 байт из `docs/Random.h`.
Пары `(stream, tier)` в ответе должны быть уникальными, как требует правило
регистрации контракта. Любой дубликат делает весь ответ статуса некорректным;
из противоречивой пары не выбирается ни одна запись.

Смещение публикации взято из `TICK_TRANSACTIONS_PUBLICATION_OFFSET = 2` и
`processTick()` в Core `src/qubic.cpp`, ревизия
`f55b46126c99a1c3f3266164c744b3d0cd694d9c`. Доставка до исполнения сама по себе
не означает включение; транзакция должна достичь лидера до отбора. Основная
политика retry неизменных байтов по-прежнему ограничена неизменным target.

Commitment, раскрываемый на `T`, отправляется в том же стриме на `T - 3`,
набор транзакций которого выбирается на `T - 5`. Ограничение reveal четырьмя
тиками помещает первое раскрытие после этого выбора при корректных наблюдениях
тика backend и указанном расписании Core. Это не доказательство финальности
консенсуса и не защита от злонамеренного лидера или ложных сообщений о тике.

Транспортный retry и дополнительная отправка могут несколько раз передать
одинаковые подписанные байты.
Если они дважды достигнут контракта в target tick, `Random.h` отклонит второй
обычный reveal через same-tick flag, а второй first commit — потому что provider
уже существует; оба пути возвращают средства без повторной мутации состояния.

## Счётчики доставки и мониторинг пустых тиков

Engine хранит накопительные за время жизни процесса счётчики финансовых
исходов. Обычный `reveal + commit`, принятый backend, сначала учитывается как
`ok`. Временные broadcast-ошибки не считаются. Наступление неизменного target
без принятия записывает один `failed`. Три согласованных наблюдения отсутствия
или отставания подтверждения, замораживающие активную локальную цепочку,
переносят её первый неподтверждённый обычный target из `ok` в `failed`;
свидетельство foreign writer этого не делает. Один target не считается дважды,
а последующие подписанные вызовы недоверенного хвоста не добавляют failures:
после первого пропущенного reveal `Random.h` удаляет provider и возвращает
средства отклонённых последующих вызовов.

Первые commits исключены. Успешные terminal reveals также не увеличивают `ok`,
но неудачная попытка terminal reveal или истечение уже предпринятой terminal-
попытки записывает один `failed`, потому что может оставить outstanding
collateral под no-show веткой контракта. Terminal, который не пытались отправить
после ошибки prerequisite, не учитывает тот же collateral второй раз.

Принятый или неудачный финансовый target один раз ставится в очередь отложенной
проверки. По умолчанию проверка разрешена через 10 тиков, одновременно активна
не более чем одна проверка, а интервал сканирования равен 600 мс. Положительные
значения настраиваются через `--reveal-verify-after` и `--empty-check-ms`.
Ошибка backend или timeout возвращает проверку в очередь без изменения
счётчиков. Каждая попытка имеет таймаут две секунды. Ожидающие targets
переводятся в готовые только после задержки в тиках; самый свежий допустимый
target имеет приоритет перед старыми проверками и повторами. Ошибка
откладывает проверку этого target на 1, 2, 4, 8, 16, затем 30 секунд для
последующих повторов внутри окна мониторинга. Интервал сканирования
продолжает ограничивать все запуски.

Окно мониторинга заканчивается через 32 тика после настроенной задержки
допуска (через 42 тика после target по умолчанию); последний тик включён.
Более старые ожидающие и готовые проверки удаляются, а старая активная
проверка отменяется до того, как её результат сможет изменить счётчики.
Граница удаления не движется назад внутри эпохи, поэтому старые проверки
нельзя поставить в очередь повторно. Дедупликация охватывает ожидающие,
готовые, активные и завершённые проверки внутри окна; граница заменяет
просроченные записи дедупликации. Истечение окна оставляет существующий исход
непроверенным и не классифицирует его как пустой или неудачный. Пропущенные
проверки сообщаются суммарно не чаще раза в минуту. Это локальный бюджет
мониторинга, а не окно приёма транзакций контрактом. Сброс эпохи очищает окно
и все проверки. Непустой результат сохраняет текущий исход, пустой переносит один
результат из `ok` или `failed` в `empty`.

Пустой означает, что выбранный backend не сообщает данных или транзакций для
target tick в целом. Это не доказывает, была ли исполнена транзакция этого
клиента. RPC использует tick data, Bob — transfers-ответ для одного тика, а
QubicLightNode — `GetTickTransactions`. Pending-проверки удаляются при reset
эпохи или drop процесса, их уже учтённый исход не меняется, а мониторинг не
задерживает drain или корректное завершение. Поэтому terminal failure при
shutdown может остаться `failed`, если процесс завершился до отложенной
проверки. Три счётчика сохраняются между эпохами и добавляются к логам после
первого результата.

Ответ QubicLightNode выводится из Core `TickData` точного размера только после
проверки запрошенного тика, назначенного лидера, уникальности ненулевых
digest-ов, активного computor-ключа из списка, аутентифицированного арбитратором,
K12 digest и FourQ-подписи. Отсутствие состояния аутентификации означает
недоступное наблюдение, а не пустой тик.

`GetTickTransactions` также возвращает все ненулевые 32-байтовые хеши транзакций
в порядке слотов Core; `digests_complete=true` выставляется только после
успешной аутентификации, в том числе для пустого набора. gRPC-адаптер отклоняет
другой тик, несогласованный признак наличия транзакций, хеши неверного размера,
нулевые или повторяющиеся хеши и наборы больше 4096 слотов Core. Старые ответы
без признака полноты сохраняют результат наличия транзакций, но не дают
сведений о включении. RPC и Bob пока предоставляют через этот порт только
прежние наблюдения о наличии транзакций.

Перед попыткой обычной или terminal-отправки движок сохраняет для target K12
полных неизменных подписанных байтов. При существующей отложенной проверке он
сравнивает все 32 байта с полным набором хешей и пишет
`TickData inclusion for target T: included`, `missing` либо `unknown`. Это
бинарный ID транзакции, независимый от отображаемого ID в ответе backend.
Хеши удаляются после успешной проверки, истечения окна или сброса эпохи;
при ошибках они сохраняются на ограниченное окно повторов. Проверяются только
существующие финансовые targets: новые проверки first commits и успешных
terminal reveals не добавляются. Наблюдения о включении не меняют финансовые
счётчики, решения о перезапуске или отправку. Доверенный локальный LightNode
аутентифицирует TickData лидера, но не финальность консенсуса или успешное
исполнение контракта.

QubicLightNode поддерживает получение computor-ключей в течение всей peer-
сессии. Он проверяет аутентифицированную эпоху с интервалом reconnect и снова
запрашивает ключи, если она не совпадает с наблюдаемой эпохой; задержка повторов
ограничена 30 секундами. Само получение ответа не означает готовность:
проверенный набор должен быть применён.

## Машина состояний стрима

| Состояние | Значение | Основные выходы |
| --- | --- | --- |
| `Waiting` | Нет пригодной локальной цепочки; ожидание свежего отсутствия или окна restart target. | `Starting` после допустимого absent-ответа; остаётся при занятости. |
| `Starting` | Свежий first commit и прогнозное продолжение известны локально; старые замороженные вызовы могут ещё доставляться. | `Active` после owned-ответа; `Restarting` после трёх согласованных допустимых absent- или foreign-ответов; `Draining` по запросу. |
| `Active` | Локальная reveal/commit цепочка непрерывно продолжается. | `Restarting` после трёх согласованных наблюдений status absence, foreign target или отставания подтверждений; `Waiting` после пропущенного target; `Draining` по запросу. |
| `Restarting` | Статус сделал локальную цепочку недоверенной. Планирование этой цепочки заморожено, но уже подписанный шеститиковый хвост сохраняет обычную политику доставки. | `Starting` после допустимого отсутствия точного слота, даже до завершения хвоста; иначе `Waiting` после завершения хвоста либо `Drained`, если запрошен epoch drain или shutdown. |
| `Draining` | Обычное планирование заморожено, terminal reveal следует за хвостом. | `Drained` после принятия или ошибки/истечения. |
| `Drained` | Новые транзакции в этой эпохе или shutdown не создаются. | `Waiting` только после смены номера эпохи. |

Цепочка владеет first target, подписанным хвостом, outstanding preimage и
неизменными транзакциями. При совмещённом restart её очередь вызовов также
сохраняет старые подписанные вызовы и их незавершённые задачи. Targets ниже
нового first target остаются только для доставки: они не могут подтверждать
новую цепочку, вызывать её остановку или блокировать terminal reveal.
Дополнительный флаг состояния не нужен: их отличает граница first target.
Недопустимые комбинации выражаются enum и `Option<Chain>`, а не независимыми
флагами.

## Restart по статусу

Engine постоянно выполняет не более одного `GetProviderStatus` запроса.
Transport failure, timeout или некорректный ответ отбрасывается, а текущие
цепочки не меняются. Каждый успешно декодированный ответ напрямую
классифицирует точный `(stream, tier)` как owned, absent или foreign.

Owned-ответ содержит `lastUpdateTick` из непрерывной подписанной локальной
последовательности targets. Цепочка хранит наибольший такой тик как watermark
подтверждений. Для status-запроса, начатого на тике `R`, наступившими считаются
только подписанные targets ниже `R`. Цепочка хранит только одно status-подозрение:
повторяющееся отсутствие, нерегрессирующие foreign targets или один и тот же
первый наступивший неподтверждённый target. Evidence должно совпасть в трёх
успешно декодированных наблюдениях со строго возрастающими тиками запроса.
Смена evidence начинает серию заново с единицы; повторные или регрессирующие
тики запроса не учитываются. Продвижение сбрасывает подозрение, а ответ ниже
watermark считается stale и не подтверждает отставание. Для `Starting`
отсутствие и foreign targets игнорируются, пока ответ не был запрошен после
возможного исполнения first target.

Повторное подтверждение без продвижения watermark не может сбросить
status-подозрение, если тик его запроса не превышает последний тик запроса
этого подозрения. Фактическое продвижение подтверждения по-прежнему сбрасывает
подозрение.

Первые два согласованных наблюдения логируются как незавершённые подозрения, а
обычное планирование продолжается. Третье status absence, нерегрессирующий
foreign target или неизменившееся отставание подтверждений замораживает текущий
подписанный хвост вместо его отмены. Новые вызовы не продолжают старую цепочку, а
все уже подписанные вызовы до старого шеститикового горизонта сохраняют retry
неизменными байтами до принятия backend или истечения target. Истечение одного
вызова во время такой замороженной досылки не запрещает попытки более поздних
подписанных вызовов. После наступления target хвоста его оставшиеся транзакции
удаляются. Outstanding preimage удаляется при подготовке replacement либо при
завершении старой цепочки без replacement. Для старой цепочки terminal reveal
не создаётся, потому что её outstanding preimage больше не считается доверенным.

Replacement по-прежнему требует успешно декодированного наблюдения об
отсутствии точного слота. Допустимое отсутствие, увиденное во время замороженного
хвоста, сохраняется, если до подготовки replacement более поздний статус снова
не сообщает занятый слот. В активной эпохе это отсутствие разрешает немедленно
подготовить replacement, не дожидаясь target старого хвоста. Первый target —
тик нужного стрима не раньше одновременно `current + 6` и `old_tail + 3`;
если он дальше, broadcast ждёт фиксированного шеститикового окна. Слот
переходит в `Starting`, сохраняет неизменные байты и retry-задачи старых
вызовов и планирует новую цепочку обычным образом. После подготовки
replacement следует обычным правилам статуса `Starting` и никогда не
перенацеливается. Старые вызовы истекают независимо, без нового финансового
failure; их принятие backend сохраняет прежнюю политику счётчиков и
мониторинга. Просроченные старые вызовы удаляются вне drain; во время drain
они освобождаются вместе с завершённой цепочкой.

После локально пропущенного target новая цепочка разрешается одним
absent-ответом из запроса, начатого после разрыва. Клиент не использует
speculative terminal reveal для восстановления после ошибки.

В `Waiting` и `Restarting` минимальный тик запроса для свежего отсутствия
никогда не уменьшается. Ответ о занятом слоте сбрасывает свидетельство отсутствия,
но старый запрос не может снизить границу, установленную разрывом цепочки или
более новым статусом.

Если скачок тика проходит следующий ещё не запланированный вызов, продление
останавливается до создания накопившихся просроченных транзакций. Сначала
обрабатывается истечение уже запланированных вызовов; иначе первый пропущенный
незапланированный reveal учитывается как один отказ. Цепочка удаляется, а
перезапуск по-прежнему требует свежего наблюдения отсутствия. Это ограничивает
работу по подписанию после обрыва связи без пропуска звеньев действующей цепочки.

## Жизненный цикл эпохи

Wall-clock граница — среда 12:00 UTC. По умолчанию engine начинает pre-epoch
drain в последние 600 секунд. Интервал задаётся
`--stop-before-epoch-end-secs`.

При новом номере эпохи удаляются все status- и tick-data-запросы предыдущей
эпохи, broadcast-задачи, подписанные транзакции и preimages. Каждый стрим возвращается
в `Waiting` и требует нового status-наблюдения. Enrollment приостанавливается до
`initial_tick + 50` по умолчанию и настраивается через
`--resume-after-epoch-start-ticks`.

Текущая совместимая схема QubicLightNode не предоставляет initial tick эпохи.
Adapter использует первый структурно корректный tick от peer, увиденный в
эпохе, как консервативный локальный initial tick, в том числе при запуске
процесса.

## Pre-epoch drain

Pre-epoch drain намеренно сохранён:

- остановить enrollment и обычное продолжение цепочек;
- сохранить уже подписанный обычный хвост и outstanding preimage;
- добавить один `reveal + zero commit` через три тика после хвоста;
- дождаться принятия backend всех обычных prerequisite перед terminal;
- повторять неудачные prerequisites и terminal неизменными байтами до принятия
  или истечения target;
- после завершения или истечения оставаться idle до новой эпохи.

Слот без известной цепочки не требует terminal-вызова. Во время drain статус
контракта не используется для запуска replacement.

Если status recovery ещё не подготовил replacement, pre-epoch drain позволяет
завершить старый замороженный подписанный хвост, но не добавляет terminal reveal
и не запускает replacement. Если replacement уже подготовлен, drain завершает
новую цепочку обычным образом; сохранённые старые вызовы не являются
prerequisites для её terminal reveal. После этого слот остаётся drained до
новой эпохи.

## Корректное завершение

События завершения Windows console и Unix `SIGINT`, `SIGTERM`, `SIGQUIT`,
`SIGHUP` замораживают обычное планирование. Каждая известная цепочка сохраняет
запланированный обычный хвост и добавляет terminal reveal через три тика.

После завершения наблюдателя shutdown engine также переходит в drain напрямую
по локальному состоянию, даже если запрос тика завершился ошибкой. Слоты без
цепочки завершаются без восстановления сети. Подготовка terminal reveal не
отправляет его: отправка по-прежнему требует свежих данных тика и соблюдения
существующей четырёхтиковой границы раскрытия.

Цикл повторно проверяет токен остановки после ожидания данных тика и обработки
завершённых задач, непосредственно перед выбором планирования или drain. Сигнал
во время этих ожиданий не позволяет начать или продлить обычные цепочки на
основании устаревшего снимка состояния остановки.

Обычные prerequisites повторяются неизменными байтами, пока target в будущем.
Terminal ждёт принятия backend всех prerequisites и входа target в
четырёхтиковое окно. При shutdown выполняется одна terminal broadcast-попытка на
managed stream, после чего процесс завершается, когда все стримы закончены.
Последующий contract status не ожидается.

Неудачный или истёкший prerequisite, неудачная terminal-попытка либо 90-секундный
deadline приводят к ошибке shutdown.

Если shutdown начинается во время pre-epoch drain, он ждёт уже замороженный
drain под тем же общим deadline и не создаёт вторую terminal-транзакцию.

Если shutdown начинается во время status recovery до подготовки replacement,
он ждёт уже замороженный подписанный хвост под тем же deadline и не создаёт
terminal reveal для недоверенной цепочки. Подготовленный replacement
завершается обычным drain, без зависимости его terminal reveal от сохранённых
старых вызовов.

## Граница backend

Каждый backend реализует только четыре операции:

- получить epoch/current/initial tick и нормализованную длительность тика;
- сообщить, содержит ли исторический тик данные или транзакции, с необязательным
  полным аутентифицированным набором хешей для проверки включения;
- запросить функцию контракта с raw input/output;
- отправить точные байты подписанной транзакции и вернуть непустой transaction
  identifier.

В клиенте нет операции balance и balance-gated enrollment.

Ошибки операций чтения называют backend и операцию, но не включают текст
транспортной ошибки, строки ошибок сервера или исходные тела ответов.
Допускается вывод кодов статуса gRPC и числовых кодов ошибок JSON-RPC.
Это исключает попадание учётных данных из ответов сервера и URL транспорта
в журнал выполнения.

В журнале принятия короткий ID транзакции вычисляется локально из K12-хеша
неизменных подписанных байтов. Идентификаторы из ответа backend не выводятся
в журнал: даже успешный ответ может повторять чувствительное содержимое запроса.
Это не меняет проверку принятия backend и правила повтора тех же байтов.

Успешные HTTP-ответы RPC и Bob ограничены 16 МиБ до разбора JSON.
Проверяются и объявленный Content-Length, и поступающие chunks; размер ровно
на границе лимита допустим. Превышение означает недоступное наблюдение либо
неудачную попытку отправки, но не пустые данные или принятую транзакцию.
Тела HTTP-ошибок отбрасываются без чтения. Лимит ограничивает буфер входных
байтов, а не все выделения памяти для JSON. Существующие таймауты engine и
правила повтора идентичных байтов сохраняются. Транспорт использует уже имеющуюся
зависимость reqwest 0.12 и её реализацию TLS; ревизия SCAPI, построение и подпись
транзакций остаются прежними.

Нормализация суффиксов endpoint и построение пути операции изменяют только часть
до первого разделителя query или fragment. Query-параметры и их percent encoding
сохраняются, включая завершающие слеши в значениях. Fragment остаётся локальными
метаданными URL и не передаётся HTTP-клиентом. Ни query-параметры, ни fragment
не включаются в диагностику endpoint.

- RPC использует `/live/v1`, `/query/v1` для tick data и base64. Ненулевой ответ
  с данными тика должен указывать запрошенный тик, даже если список транзакций пуст.
  Другой тик означает недоступное наблюдение с повтором; такой ответ не может
  изменить счётчики мониторинга. Значение null для tick data сохраняет прежнюю
  интерпретацию отсутствия данных как пустого тика. Broadcast-ответ
  принимается только при достижении хотя бы одного peer. Нулевая длительность
  нормализуется до 1 000 мс.
- Bob использует JSON-RPC, гибкое извлечение результата, transfers-запросы
  одного тика, монотонные nonce и hex. Декодируемый hex-ответ должен состоять
  из полных пар шестнадцатеричных ASCII-символов; знаки, пробельные и Unicode-символы
  отклоняются без вывода содержимого ответа.
  Ответы JSON-RPC с полем `jsonrpc` должны повторять числовой ID запроса.
  Конверты старого формата с `result`/`error` и явно заданным ID также должны
  совпадать по ID. Результаты без конверта и старые конверты без ID сохраняют
  поддерживаемую интерпретацию; поле `id` в объекте транзакции без конверта не
  считается ID конверта. Сверка ID выявляет несовпадающие ответы, но не ложные
  данные сервера.
  Поле `error` со значением null считается отсутствующим; любое другое значение
  `error` имеет приоритет над результатом. Каждая операция проверяет обязательные
  поля результата.
  Ошибки JSON-RPC показывают только целочисленный код ошибки, если он есть;
  сообщения и данные сервера исключены, поскольку могут повторять секретные
  данные запроса.
  Альтернативные поля ID транзакции проверяются по порядку до строкового значения;
  null и значения другого типа не скрывают следующее поддерживаемое поле.
  Пустой ID по-прежнему считается ошибкой.
  Планирование использует `currentVerifyLoggingTick`, а не `lastSeenNetworkTick`.
  Отставание verification может задерживать доставку; локальный Bob сам по себе
  не гарантирует своевременное включение и не аутентифицирует прогресс сети.
- gRPC использует минимальный сгенерированный клиент QubicLightNode, raw bytes
  и `GetTickTransactions`. Отсутствующие initial tick и duration заменяются
  консервативным fallback и 1 000 мс.

gRPC-адаптер перед отправкой журналирует целевой тик и полный локально
вычисленный digest транзакции для последующей проверки включения. Он никогда
не журналирует подписанные байты или preimages.

QubicLightNode по умолчанию предлагает каждую локально отправленную транзакцию
шести подключённым peers. Согласованная пользователем адаптация доступности
`--broadcast-fanout` допускает 1–32 прямых получателя в пределах числа подключений.
Она сохраняет подписанные байты, бюджеты очередей, ограничения частоты запросов
и смысл подтверждения постановки в очередь. Увеличение fanout повышает трафик
и не доказывает включение.

QubicLightNode также оценивает RTT и актуальность тиков peers в отдельной
ограниченной фоновой задаче. Она проверяет запасное соединение до замены
незанятого старого peer, требует повторных наблюдений и существенного улучшения
RTT либо устойчиво плохих результатов и применяет cooldown. Временный кандидат
добавляет не более одного сокета сверх рабочего числа исходящих соединений.
Отправки никогда не ждут подбора; граница T-4, повторы и подписанные байты клиента
не меняются. Эта согласованная политика доступности не является аутентификацией
или гарантией своевременного включения.

QubicLightNode локально проверяет подписи транзакций, но tick status поступает
из одного структурно корректного `BroadcastTick` или `RespondCurrentTickInfo`
без проверки подписи или кворума. Обычный RPC функции контракта также
возвращает первый принятый ответ peer после проверки актуальности на той же
сессии. Каждый запрос фиксирует эпоху/тик кеша и запрашивает Core
`RespondCurrentTickInfo` у не более чем трёх пиров. Запрос контракта разрешён
только пирам той же эпохи с отставанием от snapshot не более одного тика.
Нулевой статус или отсутствие опорного значения означают недоступность. Оба
этапа используют существующий общий deadline; отсутствие допустимого результата
является ошибкой, а не отсутствием provider. Обычное отставание не штрафует пир.
Этот фильтр — согласованная пользователем адаптация доступности, а не
аутентификация; он по-прежнему зависит от неаутентифицированного кеша.
Клиент напрямую использует эти ответы, как
и для RPC и Bob. Для QubicLightNode это peer-trusted данные, а не
криптографическая аутентификация или доказательство консенсуса Qubic.

## Модель отказов и безопасности

- Ошибки цикла, статуса, broadcast и проверки данных тика логируются и
  повторяются по своим правилам; остальные стримы продолжают работу.
- Пустые transaction IDs и некорректный вывод контракта отклоняются.
- Арифметика target проверяется либо насыщается там, где clamp намерен;
  переполнение не создаёт обёрнутый target.
- Баланс не проверяется заранее. Отклонённый first commit в итоге выглядит как
  свежее отсутствие в статусе и проходит обычный fresh-chain restart.
- Seed, preimages, подписанные байты, credentials, query parameters и fragments
  не должны попадать в логи, ошибки, `Debug` или persisted runtime state.
  Диагностика CLI исключает исходные поля seed и endpoint; диагностика адаптеров
  RPC/Bob исключает внутренние транспортные клиенты, которые могут хранить
  учётные данные endpoint.
  Диагностика `RevealAndCommitInput` скрывает весь вход, включая preimages.
- Только один процесс может писать для identity/tier. Foreign target
  конкурирующего writer обнаруживается в provider-status ответе выбранного
  backend. `GetProviderStatus` не может различить двух writers с одним target
  tick стрима; такой конфликт обнаруживается только после более позднего foreign
  update или исчезновения. QubicLightNode получает contract output из одного
  peer-trusted ответа.
- Broadcast раскрывает reveal backend и P2P-пирам Core. Вызовы с reveal не
  должны уходить раньше наблюдаемого `T - 4`. Это закрывает прежнее окно
  раскрытия клиентом на `T - 6`, но предполагает, что backend не сообщает тик,
  опережающий соответствующий прогресс сети. Все адаптеры по-прежнему доверяют
  наблюдениям тика; смена транспорта не является исправлением безопасности.
- Энтропия разделена по collateral tiers: залог 10 000 по умолчанию — tier 4,
  он не вносит вклад в tier 0. Оператор должен явно выбрать tier, который хочет
  поддерживать. Клиент не может изменить on-chain комиссии или гарантировать
  несмещённую энтропию при избирательном withholding другими провайдерами.

Клиент не гарантирует reveal, если процесс, host, сеть или backend недоступны до
target tick. Потеря залога при таком сбое — неотъемлемый риск commit/reveal.

## Контрольный список согласованности изменений

Перед реализацией нужно полностью прочитать английскую версию, определить
затронутые инварианты и проверить `docs/Random.h` для contract-facing работы.
Перед завершением нужно сопоставить итоговый diff и поведение с английской

известных противоречий.
